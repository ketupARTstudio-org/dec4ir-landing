## 1. What is Next.js?

Next.js is a **React framework** built on top of Node.js. Plain React only runs in the browser — Next.js adds:

- **Server-side rendering** — components can render on the server and send finished HTML to the browser (faster first load, better SEO)
- **File-based routing** — the folder/file structure under `app/` automatically becomes URL routes, no manual router config needed
- **Built-in optimisations** — image optimisation, font loading, code splitting, caching
- **Production tooling** — `next build` compiles, bundles, and tree-shakes everything into a deployable output

This project uses **Next.js 16** with the **App Router** (introduced in Next.js 13, now the default).

## 2. App Router — The Core Concept

### File Conventions

The App Router uses specific filenames to define behaviour. The two most important:

| File | Purpose |
|---|---|
| `layout.tsx` | Wraps pages — persists across navigation, renders once |
| `page.tsx` | The actual page content for a given URL route |

### How `layout.tsx` and `page.tsx` Connect

You never import `page.tsx` into `layout.tsx` manually. **Next.js does it automatically.** When a request comes in for `/`, Next.js:

1. Renders `app/page.tsx`
2. Injects its output as the `children` prop into `app/layout.tsx`

```
app/
  layout.tsx   ← the "frame" (always present)
  page.tsx     ← the "picture" (swapped per route)
```

If you add `app/about/page.tsx`, the same `layout.tsx` wraps it automatically — no changes needed to the layout.

```
/          → layout.tsx wraps app/page.tsx
/about     → layout.tsx wraps app/about/page.tsx
```

### Nesting Layouts

You can nest layouts by adding a `layout.tsx` inside a subdirectory. Each nested layout wraps only the pages in its subtree, while the root layout still wraps everything.

```
app/
  layout.tsx          ← root layout (wraps all pages)
  page.tsx            ← home page
  dashboard/
    layout.tsx        ← dashboard layout (wraps only dashboard pages)
    page.tsx          ← /dashboard
    settings/
      page.tsx        ← /dashboard/settings
```

## 3. Key Config Files

### `next.config.ts`

The main Next.js configuration file. In this project it contains one setting:

```ts
const nextConfig: NextConfig = {
  output: 'standalone',
}
```

`output: 'standalone'` tells Next.js to produce a self-contained build in `.next/standalone/` — only the files needed to run the app, without the full `node_modules`. This is what keeps the Docker image small.

### `tsconfig.json`

Configures the TypeScript compiler. Key settings explained:

| Setting | Effect |
|---|---|
| `"strict": true` | Enables all TypeScript safety checks. Catches type errors before runtime. |
| `"target": "ES2017"` | Compiles TypeScript down to JavaScript that modern browsers understand. |
| `"paths": { "@/*": ["./*"] }` | The `@/` import alias. Write `@/components/Navbar` from anywhere instead of `../../components/Navbar`. |
| `"moduleResolution": "bundler"` | Resolves imports the same way Next.js/webpack does internally. |
| `"noEmit": true` | TypeScript only type-checks — it never writes `.js` output files. Next.js handles the actual compilation via its own bundler. |
| `"plugins": [{ "name": "next" }]` | Gives your editor Next.js-aware type checking (e.g. flags incorrect Server Component usage). |

### `next-env.d.ts`

**Auto-generated by Next.js — never edit this file.**

It loads all type definitions that Next.js ships (types for `next/image`, `next/link`, `Metadata`, etc.) into TypeScript. Next.js regenerates it on every `npm run dev` or `npm run build`.

### `global.d.ts`

Project-authored type declaration file. In this project it makes next-intl's translation keys type-safe:

```ts
import en from './messages/en.json'
type Messages = typeof en

declare global {
  interface IntlMessages extends Messages {}
}
```

This tells next-intl what shape all translation messages have. If you call `useTranslations()` with a key that doesn't exist in `en.json`, TypeScript errors immediately — no silent `undefined` at runtime.

### `postcss.config.mjs`

Configures PostCSS, the CSS transformation pipeline. In this project it runs `@tailwindcss/postcss`:

```
globals.css  →  PostCSS + @tailwindcss/postcss  →  plain browser CSS
```

Your browser cannot natively understand `@import "tailwindcss"` or utility classes like `bg-base`. PostCSS converts them to standard CSS during the build. This runs automatically — you never call it directly.

### `eslint.config.mjs`

Configures ESLint, the code linter. ESLint statically analyses your code and flags problems before you run it.

This project applies two Next.js rule sets:

- **`core-web-vitals`** — enforces performance best practices (e.g. warns when you use a plain `<img>` instead of Next.js `<Image>`, which is optimised)
- **`typescript`** — TypeScript-specific rules (warns about `any` types, unused variables, etc.)

Run with `npm run lint`. VSCode also shows violations as underlines in real time via the ESLint extension.

## 4. Server vs Client Components

This is the most important conceptual shift in Next.js App Router compared to older React apps.

### Server Components (default)

Every component in the `app/` directory is a **Server Component by default**. They:

- Render on the server
- Send finished HTML to the browser
- Ship **zero JavaScript** to the client for that component
- Cannot use browser APIs (`window`, `localStorage`, event listeners)
- Cannot use React hooks (`useState`, `useEffect`, etc.)

Use Server Components for static content — anything that doesn't need to respond to user interaction.

### Client Components

Add `'use client'` at the very top of the file to opt a component into client-side rendering:

```tsx
'use client'

import { useState } from 'react'

export default function Counter() {
  const [count, setCount] = useState(0)
  return <button onClick={() => setCount(count + 1)}>{count}</button>
}
```

Client Components:
- Run in the browser
- Can use hooks (`useState`, `useEffect`, etc.)
- Can access browser APIs (`window`, `localStorage`, `navigator`)
- Do ship JavaScript to the browser

### Decision Guide

| Need | Use |
|---|---|
| Display static text, dates, lists | Server Component |
| `useState` or `useReducer` | Client Component |
| `useEffect` | Client Component |
| `localStorage` / `window` | Client Component |
| Click handlers, form inputs | Client Component |
| Fetch data (no interactivity) | Server Component |

### In This Project

| Component | Type | Reason |
|---|---|---|
| `LocaleProvider.tsx` | Client | Manages locale state, reads localStorage |
| `Navbar.tsx` | Client | Hamburger menu, language toggle |
| `HeroCarousel.tsx` | Client | Carousel autoplay logic |
| `AccordionItem.tsx` | Client | Expand/collapse on click |
| `About.tsx`, `EventSchedule.tsx`, etc. | Server | Static display content only |

## 5. React Patterns — `children` and Providers

### The `children` Prop

In React, whatever you nest between a component's opening and closing tags is passed to it as a special prop called `children`. React handles this automatically.

```tsx
<LocaleProvider>
  <Navbar />        ← these become "children"
  <main>...</main>  ←
</LocaleProvider>
```

In the component definition, you destructure it from props and render it wherever needed:

```tsx
export function LocaleProvider({ children }: { children: React.ReactNode }) {
  return (
    <SomeContext.Provider>
      {children}    ← renders whatever was nested inside
    </SomeContext.Provider>
  )
}
```

`React.ReactNode` is the TypeScript type for "anything React can render" — JSX elements, strings, numbers, arrays, `null`.

### Provider Pattern

A **Provider** is a component that uses React Context to make data available to any descendant component without passing props manually through every level.

```
LocaleProvider        ← holds locale state, exposes setLocale()
  └── Navbar          ← calls useLocale() to get current locale + toggle function
  └── main
        └── About     ← calls useTranslations() to get translated strings
        └── FAQ       ← same
```

`Navbar` and `About` don't need to receive the locale as a prop from `page.tsx` — they read it directly from context. This is how the whole app knows the current language without prop drilling.

## 6. Tailwind CSS 4 & PostCSS

Tailwind CSS 4 works differently from v3. Key changes:

**Import syntax** — use this (not the old `@tailwind` directives):
```css
@import "tailwindcss";
```

**Theme definition** — custom design tokens go inside `@theme inline {}` in `globals.css`:
```css
@theme inline {
  --color-base:    #050f1e;
  --color-accent:  #00d4ff;
}
```

These CSS custom properties automatically become Tailwind utility classes:
- `--color-base` → `bg-base`, `text-base`, `border-base`
- `--color-accent` → `bg-accent`, `text-accent`, `ring-accent`

No `tailwind.config.js` needed — configuration lives entirely in `globals.css`.

## 7. Project Folder Responsibilities

```
app/                    Next.js routing layer only
  layout.tsx            Root layout — fonts, global providers, Navbar
  page.tsx              Home page — composes all section components
  globals.css           Design system — CSS variables, Tailwind theme, global styles

components/
  layout/               Persistent UI (Navbar, Footer) — appear on every page
  sections/             One component per page section (Hero, About, FAQ, etc.)
  ui/                   Reusable primitives (AccordionItem, HeroCarousel, TabWidget)
  providers/            React Context providers (LocaleProvider)

data/                   Static content as TypeScript objects
  schedule.ts           Event phase dates
  categories.ts         Competition categories and certificate tiers
  organizers.ts         Organizer names, logos, links
  merchandise.ts        Merch items and Shopee links
  platform-features.ts  Feature tab content
  faq.ts                FAQ questions and answers
  contact.ts            Contact details

lib/                    Pure utility functions (no JSX, no hooks)
  locale.ts             detectLocale() and saveLocale()

messages/               i18n translation files
  en.json               English
  bm.json               Bahasa Malaysia

public/                 Static assets served at root URL
  media/hero/           Hero carousel GIFs/videos
  logos/                DEC4IR logo, organizer logos
  merchandise/          Merch product images
```

### The Rule for Each Folder

- **`app/`** — only routing files (`layout.tsx`, `page.tsx`, `globals.css`). No business logic here.
- **`components/sections/`** — one file per page section. Imports from `data/` and `lib/`.
- **`components/ui/`** — generic, reusable, no hardcoded content.
- **`data/`** — content only. No React imports.
- **`lib/`** — logic only. No JSX, no React imports, no UI.
- **`messages/`** — strings only. Edited when copy changes.

## 8. Request Lifecycle (End-to-End)

Here is the full journey from browser to rendered page:

```
Browser
  │
  ▼
Cloudflare Tunnel    (handles SSL/HTTPS externally)
  │
  ▼
nginx : 80           (reverse proxy, gzip, static asset caching)
  │
  ▼
Next.js app : 3000
  │
  ├─ next.config.ts  (output: standalone — tells Next.js how it was built)
  │
  ├─ app/layout.tsx  (runs first — sets up HTML shell, fonts, providers)
  │     └── LocaleProvider  (client — detects locale from localStorage)
  │           └── NextIntlClientProvider  (loads translation strings)
  │                 └── Navbar  (client — language toggle, mobile menu)
  │
  └─ app/page.tsx    (injected as {children} into layout)
        ├── Hero            (client — carousel autoplay)
        ├── About           (server — static content)
        ├── TournamentActivities  (server)
        ├── EventSchedule   (server)
        ├── Categories      (server)
        ├── Organizers      (server)
        ├── Merchandise     (server)
        ├── FAQ             (client — accordion state)
        ├── Contact         (server)
        └── Footer          (server)
  │
  ▼
HTML sent to browser
  │
  ▼
Browser hydrates client components (attaches JS event listeners)
  │
  ▼
LocaleProvider reads localStorage → sets locale → re-renders strings in correct language
```

**Key point:** The server renders HTML immediately (fast first paint, good SEO). Then the browser "hydrates" — React attaches to the existing HTML and makes interactive parts (carousel, accordion, language toggle) functional. Static sections (About, Schedule, etc.) never need JavaScript in the browser at all.
